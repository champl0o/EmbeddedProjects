# Урок: що цікавого в цьому проєкті

Цей проєкт виглядає як іграшка — поліцейська мигалка з машинкою на OLED — але в ньому акуратно зібрано вісім справді важливих ідей вбудованого програмування на C++ та ESP32. Розберемо їх по черзі, з посиланнями на конкретні рядки коду.

---

## 1. Неблокуючий `loop()` через `millis()`

**Проблема.** Найперший рефлекс початківця — `delay(400)`. Поки чекаємо ці 400 мс, мікроконтролер **не може робити нічого іншого**: ні читати кнопку, ні оновлювати дисплей, ні відповідати на UART. У реальній прошивці так не пишуть.

**Розв'язання.** Замість «спати», ми постійно крутимо `loop()` і дивимось на годинник:

```cpp
if (now - last >= interval) {
  last = now;
  // зробити крок
}
```

`millis()` повертає кількість мілісекунд від старту. Ми запам'ятовуємо момент останньої дії в `last` і виконуємо крок лише коли минув потрібний інтервал.

**Тонкощі переповнення.** `millis()` повертає `uint32_t` і переповнюється приблизно раз на 49 діб. Запис `now - last >= interval` працює навіть під час переповнення завдяки модульній арифметиці `uint32_t`. Якби ми писали `now >= last + interval` — після переповнення б усе зламалось.

**Де в репо.** `src/main.cpp:84-94` — увесь `loop()` побудовано на цьому шаблоні.

## 2. Кооперативний планувальник із масиву задач

**Що було спочатку.** Чотири майже однакові блоки `if (now - last >= …)` поспіль у `loop()`. Дублювання — це не тільки про красу: коли потрібно змінити шаблон таймера, доводиться правити чотири місця.

**Що зробили.** Згорнули їх у **таблицю задач** із трьох полів:

```cpp
struct Task {
  uint32_t (*intervalMs)();  // динамічний інтервал
  uint32_t last;             // коли востаннє запускали
  void (*run)(uint32_t now); // що робити
};
```

Тепер `loop()` — це 8 рядків, що проходять по всіх задачах:

```cpp
for (auto &t : tasks) {
  if (now - t.last >= t.intervalMs()) {
    t.last = now;
    t.run(now);
  }
}
```

**Чому `intervalMs` — функція, а не поле.** Більшість задач мають фіксований інтервал (`BLINK_MS = 400`), але **тик кадру патерну має змінний інтервал** — кожен патерн має свій `frameMs` (від 60 до 400 мс). Якби `intervalMs` був звичайним полем, його довелося б оновлювати щоразу при перемиканні патерну. А так — щоразу читаємо актуальне значення з самої таблиці патернів.

**Указівник на функцію — це адреса коду.** `void (*run)(uint32_t)` означає «змінна, що зберігає адресу функції, яка приймає `uint32_t` і нічого не повертає». Виклик `t.run(now)` стрибає за цією адресою. Це базова форма поліморфізму в C — і вона працює без будь-яких накладних витрат, без `virtual`, без купи.

**Де в репо.** `src/main.cpp:13-67`.

**Як додати п'яту задачу.** Один рядок:
```cpp
{newInterval, 0, tickSomething},
```

## 3. PWM і чому без гамма-корекції яскравість виглядає неправильно

**PWM (Pulse Width Modulation).** Світлодіод вміє тільки «увімкнено / вимкнено», аналогової яскравості в нього немає. Щоб імітувати проміжне світіння, ми швидко моргаємо: на 30% часу — увімкнено, на 70% — вимкнено. Око бачить це як «світить на 30%».

На ESP32 це робить периферія LEDC:

```cpp
ledcAttach(pin, 5000, 8);  // 5 кГц, 8 біт (duty 0..255)
ledcWrite(pin, 128);       // 50% яскравості
```

**Чому 5 кГц і 8 біт.** На частотах нижче ~100 Гц око бачить мерехтіння. На 5 кГц — точно ні. 8 біт (256 рівнів) — оптимальний компроміс між плавністю та простотою.

**Тепер найцікавіше — око бачить логарифмічно.** Якщо записати `ledcWrite(pin, 128)` — це фізично 50% часу увімкнено. Але око сприймає це як майже повну яскравість! І навпаки, перехід від 0 до 30 на 8-бітній шкалі виглядає різко, а від 200 до 230 — майже непомітно.

**Гамма-корекція** — це таблиця, що «розтягує» темну ділянку:

```cpp
// з src/led_driver.cpp
gamma8[10]  = 0    // зовсім нічого
gamma8[50]  = 8    // ледь видно
gamma8[128] = 64   // те, що око сприймає як середину
gamma8[255] = 255  // максимум
```

Формула, що використовується, — степенева з показником ~2.2 (стандартне значення для дисплеїв). У коді ми просто читаємо готову таблицю замість того, щоб рахувати степінь у рантаймі — це **набагато** швидше і дешевше для MCU.

**Де в репо.** `src/led_driver.cpp:6-22` (таблиця), `src/led_driver.cpp:24-27` (застосування). Подивіться на патерн **FADE** у `src/patterns.cpp:39-48` — там значення вибрані так, щоб після гамма-корекції перехід виглядав справді плавним.

## 4. `PROGMEM` і `pgm_read_byte` — спадщина AVR, що дійшла до ESP32

**Звідки взявся `PROGMEM`.** На класичному AVR (Arduino Uno, Nano) — **гарвардська архітектура**: окрема пам'ять для коду (Flash, 32 КБ) і окрема для даних (SRAM, лише 2 КБ). Якщо ви оголосите масив `const uint8_t arr[256] = {...}` без `PROGMEM`, він **скопіюється з Flash у SRAM при старті**. На AVR з 2 КБ оперативки це швидко з'їсть усе вільне місце.

Макрос `PROGMEM` каже компілятору: «залиш цей масив у Flash, не копіюй у SRAM». Але тоді читати його через звичайний `arr[i]` уже не можна — потрібен спеціальний спосіб:

```cpp
uint8_t value = pgm_read_byte(&arr[i]);
```

**Що з цим на ESP32.** ESP32 має **фон-неймановську архітектуру** з єдиним адресним простором. Flash маплений у пам'ять, і звичайне `arr[i]` працює. Тому `PROGMEM` на ESP32 — фактично **порожній макрос**, а `pgm_read_byte` — звичайне розіменування. Усе одно лишаємо їх у коді: це **переносимість** — той самий код скомпілюється і для AVR, і для ESP32, і всюди працюватиме оптимально.

**Де в репо.** Усі чотири патерни в `src/patterns.cpp` оголошені з `PROGMEM`, і ми читаємо їх через `pgm_read_byte` у `src/main.cpp:32`.

## 5. Data-driven дизайн: патерни як дані, а не код

**Як НЕ варто.** Початківець напише:

```cpp
void playPattern(int id) {
  switch (id) {
    case 0: /* WIG-WAG */ ... break;
    case 1: /* RUNNING */ ... break;
    case 2: /* QUAD-FLASH */ ... break;
    // ...
  }
}
```

Додавання нового патерну = редагувати функцію, додавати `case`, не забути в кількох місцях.

**Як зробили ми.** Кожен патерн — це **просто рядок у таблиці**:

```cpp
struct Pattern {
  const uint8_t (*frames)[CHANNELS];
  uint8_t frameCount;
  uint16_t frameMs;
  const char *name;
};

Pattern patterns[] = {
  {WIG_WAG,    2,  400, "WIG-WAG"},
  {RUNNING,    4,  120, "RUNNING"},
  {QUAD_FLASH, 16, 70,  "QUAD-FLASH"},
  {FADE_ALT,   8,  60,  "FADE"},
};
```

Код, що **відтворює** будь-який патерн, написаний один раз і **не знає** про конкретні патерни:

```cpp
Pattern &p = patterns[currentPattern];
uint8_t frame[CHANNELS];
for (int i = 0; i < CHANNELS; i++) {
  frame[i] = pgm_read_byte(&p.frames[currentFrame][i]);
}
applyFrame(frame);
currentFrame = (currentFrame + 1) % p.frameCount;
```

**Додати п'ятий патерн** = дописати один масив кадрів і один рядок у `patterns[]`. Нуль змін у логіці.

Це широковідома ідея — **розділення «що робити» (дані) від «як робити» (код)**. У великих системах саме так роблять конфігурації, правила бізнес-логіки, рівні в іграх.

**Де в репо.** `src/patterns.cpp` цілком, і `src/main.cpp:26-37` (відтворення).

## 6. `constexpr` і обчислення розмірів на етапі компіляції

**Класика C.** Скільки елементів у масиві?
```cpp
const int N = sizeof(RED_PINS) / sizeof(RED_PINS[0]);
```
Цей трюк лічить розмір на етапі компіляції — рантайму це нічого не коштує.

**З `constexpr` (C++11+) — ще краще:**
```cpp
constexpr int N = 2;
constexpr int CHANNELS = 2 * N;
```

`constexpr` гарантує, що значення відоме на етапі компіляції. Це означає:
- можна використовувати як **розмір масиву**: `uint8_t frame[CHANNELS];`
- можна як **частину типу**: `const uint8_t (*frames)[CHANNELS];`
- 0 байт пам'яті в рантаймі — це просто число у скомпільованому коді

**Чому не `#define CHANNELS 4`.** `#define` — це текстова заміна препроцесора, без типів і scope. `constexpr` — повноцінна змінна з типом, видимістю та правилами області видимості. Помилки ловляться раніше, IDE розуміє контекст, дебагер показує значення.

**Тонкість заголовків.** З C++17 `constexpr` змінна на рівні namespace **автоматично `inline`** — її можна оголосити в заголовку без проблем з ODR (One Definition Rule). До C++17 довелось би лізти в `extern` або `static`.

**Де в репо.** `include/config.h:9-13` — увесь блок констант. Подивіться, як `CHANNELS` потім «протікає» в тип `Pattern::frames`, у розмір локального буфера, у розмірність патернів — і все це автоматично. Зміните `RED_PINS = {18, 13, 14}` — і всі чотири місця компілятор поправить сам.

## 7. Розбиття на модулі: що йде в .h, а що в .cpp

**Базове правило:**
- **`.h` (заголовок)** — «що існує»: декларації функцій, типи, `extern` для глобальних змінних, `constexpr` константи.
- **`.cpp` (реалізація)** — «як саме»: тіла функцій, визначення глобальних змінних, `static` (приватні для файлу) допоміжні функції.

**Наш приклад — таблиця патернів:**

`include/patterns.h`:
```cpp
struct Pattern { ... };           // тип — у заголовку
extern Pattern patterns[];        // лише ОГОЛОШУЄМО, що десь є
extern const int PATTERN_COUNT;
```

`src/patterns.cpp`:
```cpp
static const uint8_t WIG_WAG[][...] PROGMEM = { ... };  // static — не витікає назовні
Pattern patterns[] = { ... };     // ВИЗНАЧЕННЯ — рівно одне в усій програмі
const int PATTERN_COUNT = ...;
```

**Ключове слово `static` у .cpp** робить ім'я **локальним для цього файлу** (internal linkage). Інші `.cpp` навіть не побачать імені `WIG_WAG`. Але вказівник на нього, збережений усередині `patterns[].frames`, лишається валідним — звертатись до даних можна через цей вказівник звідусіль.

Це класичний прийом інкапсуляції на C/C++: «деталі реалізації — приватні, інтерфейс — публічний», без `class` і `private`.

**Де в репо.**
- `include/config.h` — публічні константи (всі модулі бачать)
- `include/patterns.h` ↔ `src/patterns.cpp` — тип + таблиця
- `include/led_driver.h` ↔ `src/led_driver.cpp` — `applyFrame`, `gamma8` (static)
- `include/police_display.h` ↔ `src/police_display.cpp` — `drawPoliceCar`, об'єкт `display` (static)
- `src/main.cpp` — оркестрація, нічого не експортує назовні

## 8. Namespace як охайна заміна `#define`-зоопарку

**Проблема.** Десятки магічних чисел у `drawPoliceCar`: `x + 14`, `32`, `5`, `4`… Що це? Координата мигалки? Її розмір? Загубитись легко.

**Сусідня проблема.** Якщо лити всі константи в глобальну область з префіксами (`CAR_BODY_X`, `CAR_BODY_Y`, `ROAD_Y`…), виходить довго і шумно.

**Розв'язання — namespace:**
```cpp
namespace CarSprite {
  constexpr int BODY_X = 2, BODY_Y = 44, BODY_W = 36, BODY_H = 12;
  constexpr int LIGHT_Y = 32, LIGHT_W = 5, LIGHT_H = 4;
  // ...
}
```

Тепер виклик читається як підпис до картинки:
```cpp
display.drawBox(x + CarSprite::BODY_X, CarSprite::BODY_Y,
                CarSprite::BODY_W,     CarSprite::BODY_H);
```

А якщо це робиться багато разів — `using namespace CarSprite;` усередині функції імпортує імена локально:
```cpp
void drawPoliceCar(...) {
  using namespace CarSprite;          // лише в цій функції
  display.drawBox(x + BODY_X, BODY_Y, BODY_W, BODY_H);
}
```

Глобально `using namespace` тягнути не варто — буде зіткнення імен. Локально у функції — нормальна практика.

**Де в репо.** `src/police_display.cpp:9-46` — три namespace (`Screen`, `Road`, `CarSprite`) розділяють геометрію за роллю. Решта `drawPoliceCar` — це майже просто список іменованих прямокутників.

## 9. Малювання на OLED: full-buffer і трюк з кольором 0

**Дві стратегії U8g2:**
- **Page buffer** (літери `_1_`, `_2_` в назві драйвера) — економить RAM, але треба самим керувати посторінковим оновленням.
- **Full buffer** (`_F_`, наш випадок) — тримає весь екран (128×64 / 8 = 1024 байти) в RAM, малювання миттєве, але це 1 КБ оперативки.

На ESP32 з 320 КБ SRAM 1 КБ — копійки, тому беремо `_F_`. Цикл:
```cpp
display.clearBuffer();   // обнулили буфер
// малюємо багато примітивів
display.sendBuffer();    // одним I²C-блоком переслали все на дисплей
```

**Трюк з `setDrawColor(0)`.** OLED монохромний — піксель або горить, або ні. Як «вирізати» вікна в кузові машинки? Спочатку малюємо суцільний бокс кабіни:
```cpp
display.drawBox(x + 10, 36, 20, 8);   // cabin
```
А потім перемикаємось на «колір 0» (тобто «гасимо») і малюємо поверх:
```cpp
display.setDrawColor(0);
display.drawBox(x + 12, 38, 7, 5);    // window 1
display.drawBox(x + 21, 38, 7, 5);    // window 2
display.setDrawColor(1);              // повертаємось до малювання
```

Виходить машинка з вікнами «вирізаними» в кузові. Той самий трюк використовується для:
- внутрішньої втулки колеса (диск + менший «гашений» диск всередині)
- інверсного напису `POLICE` на боці кузова

**Де в репо.** `src/police_display.cpp:75-86`, `:93-101`.

## 10. Куди далі — ідеї для розширення

Усе вище — лише фундамент. Кілька напрямків, де можна попрактикуватись:

- **Кнопка для ручного перемикання патернів.** Додати ще одну `Task`, що читає GPIO, з debounce (теж через `millis()`). Натискання → `currentPattern = (currentPattern + 1) % PATTERN_COUNT`.
- **Потенціометр для швидкості.** `analogRead()` → масштабуємо у множник для `p.frameMs`. Зацікавлено подивитесь, як зміна frameMs «на льоту» автоматично проходить через наш динамічний `intervalMs()`.
- **Сирена.** ESP32-S3 має DAC; можна згенерувати трикутну хвилю частоти, що повзе вгору-вниз, і завести її на маленький динамік через підсилювач. Окрема `Task` для звуку.
- **Збереження останнього патерну в NVS** (non-volatile storage), щоб після reset мигалка продовжувала з того ж місця.
- **Більше патернів.** Спробуйте додати «SOS» (морзянка), «STROBE» (один короткий спалах раз на секунду), «POLICE-EU» (синій біжучий вогник, як у європейських машин). Це — лише один масив + один рядок у `patterns[]`.

## Підсумок: що тут «насправді» вивчили

Цей проєкт демонструє, як **дрібні правильні рішення** складаються в маленьку, але охайну систему:

1. **Часом, а не сном** — `millis()` замість `delay()`.
2. **Даними, а не кодом** — масив `Pattern` замість `switch`.
3. **Конфігом, а не магією** — `constexpr` замість `#define`.
4. **Поінтерами, а не дублюванням** — таблиця задач замість 4 if-блоків.
5. **Модулями, а не одним файлом** — кожен `.h/.cpp` відповідає за одну річ.
6. **Іменами, а не магічними числами** — `CarSprite::BODY_X` замість `x+2`.

Усі ці прийоми переносяться 1-в-1 на будь-який наступний embedded-проєкт — і на більший «дорослий» код теж.
